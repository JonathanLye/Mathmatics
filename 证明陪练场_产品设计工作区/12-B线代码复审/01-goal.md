> 用法：把下面“粘贴区”整段交给目标模式（/goal 或同类循环）。每轮开始先读 `00-复审报告.md` 的 §2，从未完成的最高优先级条目做起。

> **进度（2026-11-03 晚）**：条目 1–7 已有对应分支（见 `00-复审报告.md` §0.5），尚未开 PR、CI 未跑；条目 8（CI 真实 PG）、9 中的 P1-5/P1-8/删除权/撤回同意仍开放。重新使用本 goal 前先读 §0.5，不要重复已完成的条目。

## 粘贴区

**目标**：在 2026-11-05 晚上一个班（≈60 人，同一校园出口 IP）真实使用之前，让 B 线服务端满足下列完成条件；每条都必须有可复现的命令输出作证，没有输出的不算完成。

**完成条件（全部满足才算完成）**

1. 部署可用：`docker compose -f infra/docker-compose.yml up -d` 后，从 caddy 容器内 `curl http://server:3000/health` 返回 200；CI 里有这一步。（P0-1）
2. 迁移可重复（P1-0，不阻塞首次上线）：`pnpm db:migrate` 连续执行两次都成功，且有版本表记录已执行的迁移；有“从空库迁移 → 再迁移 → 种子”的测试。
3. 登录不被共用 IP 卡死：同一 IP 在 1 分钟内 60 人以内的合法登录全部成功；有对应测试。（P0-2）
   - 登录失败锁定**不要**按报告原样的“同邀请码失败 5 次锁 10 分钟”实现——那会让 5 次学号输错锁住全班。如果要做，必须按 (邀请码, 学号哈希) 或 (IP, 学号哈希) 计，只数凭据失败，并有“学生 X 连续失败不影响学生 Y 登录”的测试。具体策略属于**需要停下来问用户**的规格问题。
4. 写接口幂等：所有 06 §1 要求带 `Idempotency-Key` 的写接口，同键重放返回首次响应且不重复入库；`repro-login-close-device.test.ts` 的 R4 通过（同键重发两次，库里只有一行）。（P0-3；上轮复审曾把它推迟为 P1，是否现在做由用户确认）
5. 关闭后只读：布置 `closed` 或超过 `close_at` 后，作答的所有写接口返回 409 `ASSIGNMENT_CLOSED`；`repro-login-close-device.test.ts` 的 R2 通过。（P1-1）
6. 连接池稳健：`pg.Pool` 有 `error` 监听、连接/语句/空闲事务超时；`tx` 回滚失败不掩盖原错误；有测试用例模拟池错误不崩进程。（P1-2）
7. 求助留痕：`/help` 的每条路径（含施压拒绝、concept、check_line、free）都写一条 `help.request`；有测试断言事件存在且不含学生原文。（P1-3）
8. 真实 PostgreSQL：CI 增加 `postgres:16` service，同一套 server 测试在 `DATABASE_URL` 下通过；新增“两批事件以相反顺序引用同一批作答”的并发测试且不死锁。（P1-4）
9. 报告里 P1-5（登录强度）、P1-7（限流）、P1-8（教师事件班级校验）每条要么修复要么在 `00-README.md` 决策日志里有明确的“接受风险”记录并写明谁决定；§7 的“删除权 / 撤回同意”同样需要用户书面确认接受或排期。

**每个条目的工作方式**

- 先写失败的测试，贴出它失败的输出，再改实现，再贴通过的输出。
- 改动前读相关的 `10-开发文档` 章节；代码与 06 契约冲突时**停下来问**，不要自己发明规则（AGENTS.md §5）。
- 只在 `feat/b-<issue#>-<slug>` 分支上做，**不直接推 main**，不手改生成物，不提交 `.env` 或学生数据。PR 描述写“改了什么 / 为什么 / 怎么验证 / 风险”，并贴实际命令和结果。
- 每个 PR 不超过约 400 行 diff；一个 PR 只做一个条目。

**复核节奏（必须执行）**

- 每完成 2 个条目，调用一次 advisor，输入是“已完成条目 + 对应 diff + 测试输出 + 尚未解决的怀疑”，并把 advisor 的反对意见写进 PR 描述。
- 凡是涉及外部事实的结论（Fastify/pg/Caddy/PostgreSQL 行为、TypeSafe/Jev 接口、法规），用 Exa 查官方文档并在 PR 里贴 URL；查不到就标“未验证”，不得当作结论。
- 全部完成前，再调用一次 advisor 做总复核，通过后才能宣布完成。

**必须停下来问用户的情况**

- 需要改 `packages/contracts`（B 维护，但须 A/C 评审）或 06 契约字段。
- 需要在登录强度（P1-5）与失败锁定策略上做产品取舍。
- 幂等（P0-3）是现在做还是维持上轮的“推迟”。
- 任何会对外发布的动作：合并 PR、在 GitHub 评论、改仓库设置、使用真实模型密钥。

**不属于本目标**：A 的前端（只读审查，意见写进 PR 评论草稿，由用户决定是否发布）、C 的教师端、识别（SimpleTex）接入、Jev 上线。

## 评审流程补丁（建议一并采纳）

1. B 的 PR 不再由 B 自己 admin 合入；A 不在线时由 C 批，C 也不在线时由用户明确指定“可自批”的 PR 并在 PR 里写原因（U13 例外要有审计）。
2. 单 PR 超过 2000 行的，必须拆分或在描述里写“重点读哪几个文件”。
3. AGENTS.md §4 的验证命令更新为 pnpm 与 `packages/contracts`（目前两套并存）。
