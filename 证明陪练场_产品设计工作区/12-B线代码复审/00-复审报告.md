### P2

- **设备记录可被抢占**：`devices` 用 `ON CONFLICT (id) DO UPDATE SET user_id`，`deviceId` 是客户端自报的 UUID。R3 **[实测]** 两人用同一 deviceId 登录后，设备行 `user_id` 变为第二人。但全仓库没有任何代码读取 `app.devices`（`multi_device` 信号数的是 `ev.events.device_id`），所以目前无实际后果；教师端一旦展示“设备”就会受影响，届时需改成按 (user_id, device_id) 建键。
- `trustProxy: true`（生产）。当前部署下是安全的：Caddy 默认丢弃客户端自带的 `X-Forwarded-*`[Exa: caddyserver.com/docs/caddyfile/directives/reverse_proxy]，且 server 只 `expose` 不 `ports`。但 Fastify 官方说明 `true` 即信任所有跳数[Exa: fastify.dev Server reference]，一旦端口被映射出来或前面再加一层 CDN 就可伪造 IP 绕过限流。建议改成 `1` 或 Caddy 所在网段。
- `maskIp` 只处理 IPv4，IPv6 存 `null`；校园网/手机网络出现 IPv6 时，会话 IP 与限流外的审计信息都为空。
- `NODE_ENV` 未设置时静默使用写死在源码里的开发密钥（会话签名、PII 加密、学号盐）。compose 与 Dockerfile 设了 production，但手动 `pnpm start` 会失败开放。建议无 `NODE_ENV` 也要求密钥。
- PII 密文无密钥版本号，将来换 `PII_KEY` 需要整表重加密。
- 没有撤回同意书的接口（13 §2 有撤回口径）；`hasValidConsent` 已支持 `revoked_at`，缺的是路由。
- Dockerfile 以 root 运行、无 `HEALTHCHECK`；compose 的 server 无健康检查，Caddy 不会感知后端未就绪。
- `server.ts` 关闭流程无论成败都 `process.exit(0)`。
- `csvField` 没有对 `= + - @` 开头的单元格转义；当前导出列都由服务端生成（`arm` 来自教师设置），风险低，但导出给研究者在 Excel 打开时应转义。
- `AGENTS.md` §4 还写着 `10-开发文档/contracts` 与 `npm run check`，而 CI 实际用 `pnpm`、`packages/contracts`；两套并存，AI 代理按 AGENTS.md 执行会跑到旧目录。

### 我怀疑但核实后**排除**的

- `tsClient` 格式不对会让整批 500：events schema 对 `tsClient` 要求 `format: date-time` 且由 ajv-formats 校验，坏值在入库前就被标为 `schema` 拒绝。**不成立**。
- `canon()` 的 `slice(i)` 在长串反斜杠上是 O(n²)：MathText 上限 4000 字符，最坏约 800 万次字符拷贝，毫秒级。**不成立**。
